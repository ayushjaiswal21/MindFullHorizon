## 1. The rule-based floor (runs first, never calls a model)

`ai/severity.py::classify(text)` returns one of four classes:

| Class | Meaning | Detector severity | Chat | Journal |
|---|---|---|---|---|
| crisis | first-person self-harm language | 9 | Crisis card with 3 helplines; reply text is the model reply if it returned one, else the fixed crisis reply; alert created | Entry saved, warning message with helplines, alert created |
| friend | someone else is at risk | 4 | Helping-a-friend reply with helplines; no alert | No special handling (not flagged) |
| soft | negated or ambiguous distress | 5 | Gentle check-in reply with helplines; no alert | No special handling (not flagged) |
| none | nothing found | 0 | Normal reply; no helplines unless the model is blocked | No special handling |

The full phrase list is in `crisis_phrases.csv`; sentences and the detector output are in `crisis_test_cases.csv`.

## 2. Flow A: chat message (web chat, `POST /api/chat`)

1. The student must be logged in; the user id comes from the session, never from the request.
2. The message is bounded to the first limit in section 0 and passed to `ai/service.py::ask_with_severity`; the model only ever sees the cleaned, shorter text.
3. The rule-based class and severity are computed first, on the full bounded text, before anything else. Injection markers are detected but this only hardens the prompt, it never changes the floor. A per-user budget decides whether the model is called at all; over budget, a crisis message is still answered by the floor. Then the model (Gemini) is asked for a reply and its own severity. If the model fails, times out or is blocked, the rule-based result still stands.
4. Final severity is the higher of the rule-based and model severities. Decision line in code: `ai/service.py:163:     crisis = level == 'crisis' or score >= 7`.
   Friend class caps severity: `ai/service.py:159:         score = min(score, 6)  # someone else is at risk: support path, not the self-crisis card`.
5. Helplines are attached when: `ai/service.py:179:     show_helplines = crisis or level in ('friend', 'soft') or blocked or rate_limited`.
6. Which reply text is shown during a crisis:
   - AS IMPLEMENTED: the model-written reply is shown during a crisis if the model returned a usable one; the fixed `CRISIS_REPLY` is used when the model gave nothing usable. If the output guard blocks the model reply on a risk path (dosage, diagnosis stated as fact, method details, promises, leaks), the fixed text is used instead. Clinician note: the crisis wording is therefore not always the fixed text. The public page `/ai` (templates/how_ai_works.html) says a fixed reply is shown "whatever the model wrote"; that sentence and the code disagree and the owner must resolve it before any claim is made.
7. If the final decision is crisis, `routes/chat.py` writes a `CrisisEvent` (source `chat`, reason code `chat_self_harm`) and queues a `crisis_alert` job in one commit. If that write fails, the student still receives the reply and helplines and the response carries `alert_recorded: false`; an ERROR log line holds ids only.
8. A crisis can also be raised by the model alone (model severity at or above the threshold with no rule hit). It then creates an alert with the same reason code.
9. Soft and friend classes show helplines but create NO alert and NO counsellor notification.
10. Legacy socket chat (`app.py` event `chat_message`): crisis text gets the fixed `CRISIS_REPLY` and an event with severity 9; the helplines appear inside that reply text.

## 3. Flow B: journal entry

1. Title and content are joined and checked with `utils/crisis.py::text_is_crisis`, which is true only for class crisis. Friend and soft classes are NOT flagged in journals.
2. If crisis: the entry is saved and a `CrisisEvent` (source `journal`, severity 9, reason `journal_self_harm`) plus a `crisis_alert` job are written in the same transaction as the entry. If the write fails the student sees an error message and still sees the helplines.
3. The student sees a warning message with the helplines (strings below). No points are awarded for that entry.
4. The AI suggestion for a crisis entry is a fixed text with helplines; no model is called for it.

## 4. Flow C: PHQ-9 and GAD-7 (`POST /api/save-assessment`)

1. The score is always recomputed on the server from the item answers; a client-sent score is ignored.
2. An alert is raised when PHQ-9 item 9 is answered 1, 2 or 3 (reason `phq9_item9_positive`, severity 9), or when the total is severe (PHQ-9 total >= 20 or GAD-7 total >= 15; reason `phq9_severe` or `gad7_severe`, severity 7). A skipped item 9 is unanswered and raises nothing.
3. For an alert, the explanation text is fixed (no model call) and the response carries `crisis: true` plus the helplines; the assessment and the `CrisisEvent` commit together (all or nothing). If saving fails the student still gets the fixed text and helplines.
4. Event source is `phq9` for GAD-7 events as well (the database allows only chat, phq9, journal).
5. No points, badges or streaks are attached to any score.
6. Moderate scores (PHQ-9 10 to 19, GAD-7 10 to 14) raise no alert and create no counsellor task. See `assessment_bands.csv`.

## 5. Alert pipeline and escalation timeline (after any event above)

| Time | What happens | Who is told | How |
|---|---|---|---|
| T0 | Event row and `crisis_alert` job committed | nobody yet | database |
| T0 + a few seconds (worker poll 2.0 s) | `crisis_alert` job runs | every provider account whose institution text equals the student's | in-app notification only |
| T0 + 15 min | Level 1, only if nobody acknowledged | same providers | in-app notification again |
| T0 + 30 min | Level 2 | same providers, plus one configured address | in-app notification; email only if `CRISIS_ESCALATION_EMAIL` and SMTP are set |
| T0 + 45 min | Level 3 (last) | same as level 2 | in-app notification and email as above; then an ERROR log line; no further steps |

Acknowledging the event on the provider dashboard stops the chain at the next step.

Provider selection in code: `utils/crisis.py:67:     return User.query.filter(User.role == 'provider', User.institution == user.institution).all()` (exact match on the free-text institution field; a typo or a different spelling means nobody is notified).
Email condition: `utils/crisis.py:121:     if level >= 2 and target:`.

Notification text counsellors see:

> A student at your institution needs urgent follow-up. Open the dashboard to review.
> Escalation {level}: a student still needs follow-up and nobody has acknowledged the alert.

Escalation email subject: `[MindFull Horizon] Unacknowledged crisis alert (level {level})`

Email body holds the institution name, event id and time only. It never holds the student message.

Providers of the institution can also see all unacknowledged events on their dashboard without any assignment, and every acknowledgement is written to the audit log (`routes/provider.py`).

## 6. What the code does NOT do (read from the code, verify with the owner)

- No out-of-hours logic: no hour, weekday or timezone handling was found in utils/crisis.py. An alert at 02:00 follows the same timeline as one at 14:00 and waits for a counsellor to log in.
- No SMS, WhatsApp, phone call or push notification: none found in the alert code.
- Level 0 and level 1 reach counsellors only as in-app notifications. The only outbound message is the level 2 and 3 email to one configured address.
- No notification to a guardian, hostel warden, college management or police.
- No follow-up workflow: the CrisisEvent columns are id, user_id, source, severity, reason, created_at, acknowledged_at, acknowledged_by, escalated_at, escalation_level. There is no contacted, closed or follow-up field, so the three-session follow-up from the UGC draft is not tracked.
- No merging of repeat alerts: each flagged message or entry creates its own event and notifications.
- No 24x7 human behind the alerts is built into the product. Nobody is paged.
- A model failure never removes the helplines, but a database failure can lose the alert (the student is still shown help).
